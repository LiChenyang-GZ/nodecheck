# 故障演练记录：加了 2 ms 延迟，compare 却放行了

[English](2026-11-11-added-latency.md)

> **这是测试环境里有计划的故障演练，不是线上事故。** 用 blameless postmortem（不追责的事后复盘）格式来写，因为演练发现了工具的一个真漏洞。时间是 AEDT（UTC+11），2026-11-11。

## 摘要

`nodecheck compare` 拿一台机器的跑分和它自己的 baseline 比。给 node-1 发出去的每个包加 2 ms 延迟后，带宽仍是 5.65 Gbit/s，compare 以退出码 0 放行；可每个来回都多了 2.36 ms（0.46 → 2.82 ms）。compare 判带宽，延迟只显示不判。我们加了"比 baseline 多几毫秒"的延迟检查，同样的故障现在报 FAIL、退出码 1。

## 影响

- 测试环境：没有；故障是故意加的，测完马上拆掉。
- 如果是真的：一台网络来回慢了 6 倍的机器会被验收通过。机房内一个来回通常远不到 1 ms；每一步都要在机器之间交换结果的任务（比如分布式训练）会变慢，而带宽测试全过。

## 怎么发现的

演练本身：compare 的输出里延迟是 +509%，却标着 INFO（not judged），结果 `0 FAIL, 0 WARN`。

（时间取自抓回的文件和提交记录；带"~"的是按先后顺序估的。）

## 根因

1. **网络只判了一个指标。** compare 是围着带宽设计的（第一个演练测的就是带宽）。延迟测了、也显示了，但没有门槛，所以不可能 FAIL。
2. **延迟是故意先不判的，但原因还没想好怎么解决。** 0.46 ms 的 baseline 用百分比门槛不行：同一个晚上不加故障，延迟就高过 0.64 ms（+139%），按 25% 几乎每次都 FAIL。

## 怎么修的

门槛除了"占 baseline 的比例"（`warn_drop` / `fail_drop`），现在也能用"指标自己的单位"（`warn_by` / `fail_by`）。延迟：比 baseline 多 1 ms 报 WARN、多 1.5 ms 报 FAIL，高于见过的所有正常波动（+0.64 ms），低于故障（+2.33 ms）。报告里延迟写 `+2.36 ms`，不写 `+509%`。

## 做得好的

- 演练前先试测：照原计划加 5 ms，带宽也会掉，带宽检查自己就能抓到，漏洞反而看不出来。
- 用真实输出当 fixture：失败的测试用的就是 VM 上的数字。
- 调大 netem 的队伍（`limit 10000`）：默认值下加 5 ms 还会丢包（3.46 vs 3.78 Gbit/s），延迟测试里混进了丢包。

## 做得不好的

- 一次读数看错了：20:44 限速时 ping 平均 1.105 ms，以为是限速让延迟变大。21:04 有了对照（限速中 0.68 ms，前后 0.71、0.84 ms），才知道是不同时间的波动。
- baseline 在变旧：现在不加故障，延迟就在 0.7～1.0 ms，baseline 是 0.463 ms。

## 教训

- **带宽和延迟各坏各的。** 测了一个，说明不了另一个。
- **每个门槛都要选"正常波动相对故障很小"的单位。** 带宽用百分比；不到 1 ms 的延迟用毫秒。
- **没亲眼看它失败，就别信这个检查**，而且要确认演练是因为对的原因失败。
